# 브라우저 조작 성능 테스트 분석

조사일: 2026-10-26. Flowmux 코드 기준: `186afac29f8cdd4482063706467726101856c54f`.
ego(lite) 공개 SDK 기준: `aecc5831fc5a9ea01a078b632185992a3a7ac448`.

**브라우저 조작 성능은 기능 정확성, 조작 경로의 지연, 에이전트의 업무 완료 성능을 나눠 평가해야 한다.** ego(lite)는 실제 브라우저 E2E 검사와 고정 조작 시간 비교, 실제 업무 벤치마크를 각각 공개한다. 외부 에이전트 브라우저는 공개 웹 과제를 실행하고 작업 기록을 채점하는 방식을 사용한다. 각 평가의 측정 범위가 달라 점수나 시간을 하나의 순위로 합칠 수 없다.

이 문서는 공개 자료와 실행 코드의 정적 분석이다. 제품을 설치하거나 벤치마크를 새로 실행한 결과가 아니다. 비교 대상 중 하나는 요청에 따라 **외부 에이전트 브라우저**로만 표기하며, 해당 제품명·식별 URL·로고·원문 파일은 결과물에 포함하지 않는다. 공통 평가 방법의 출처는 원 벤치마크 문서로 연결한다.

## 1. 무엇을 측정하는가

| 평가 층 | 질문 | 대표 지표 | 해석 범위 |
| --- | --- | --- | --- |
| 기능 정확성 | 클릭·입력·탐색이 의도한 상태를 만들었는가? | assertion 통과, 잘못된 대상 조작, 중복 실행, 실패 원인 | 기능과 회귀 검증 |
| 조작 경로 | 같은 관찰·조작·검증 절차를 얼마나 빨리 수행하는가? | 명령 응답 시간, 결과 확인 시간, p50/p95, 출력 크기 | CLI/SDK·IPC·엔진·대기 비용 |
| 에이전트 업무 | 자연어 요청을 얼마나 잘, 빨리, 저렴하게 끝내는가? | 완전 성공률, 부분 점수, 전체 시간, 모델 호출·토큰·비용 | 모델·프롬프트·도구·사이트를 합친 시스템 성능 |
| 엔진 응답성 | 웹 앱 자체가 얼마나 빠르게 반응하는가? | Speedometer 등 | 렌더링·JS 작업 성능 |

[Speedometer](https://github.com/WebKit/Speedometer)는 모의 사용자 상호작용으로 웹 앱 응답성을 측정한다. 브라우저 조작 API의 정확성이나 에이전트 업무 성공률을 대신하는 지표는 아니다.

## 2. ego(lite)의 실제 테스트 방식

### 실제 브라우저 E2E: 기능 검증에 케이스 시간을 덧붙임

공개 SDK의 `npm run e2e`는 SDK를 빌드하고, 로컬 HTTP fixture·업로드 파일·작업 Space를 준비한 뒤 실제 브라우저에서 케이스를 순서대로 실행한다. 조사한 목록에는 69개 케이스가 있다. 탐색·입력·포인터·팝업·다운로드·미디어뿐 아니라 iframe/OOPIF, Shadow DOM, 부분 snapshot의 ref 수명, 실행 간 복귀, 지연 팝업과 timeout 복구를 검사한다.

각 케이스는 `pass/fail/skip`, `durationMs`, assertion 수, 오류 메시지를 기록한다. 시간은 CLI 프로세스 실행 전후의 `Date.now()` 차이다. 따라서 프로세스·SDK 시작과 케이스 내부의 모든 조작·대기를 포함한다. 전체 시간에는 빌드와 환경 준비도 들어간다. 반복 표본의 p95나 모델 비용을 측정하는 벤치마크는 아니다.

기본 공개 CI는 `npm test`로 빌드·타입·단위 검사를 수행하며, 별도 `e2e` 명령을 호출하지 않는다. CI 통과만으로 실제 브라우저 E2E 실행을 증명할 수 없다. 근거: [runner](https://github.com/citrolabs/ego-lite/blob/aecc5831fc5a9ea01a078b632185992a3a7ac448/package/ego-browser/scripts/real-browser-e2e/runner.mjs), [케이스 목록](https://github.com/citrolabs/ego-lite/blob/aecc5831fc5a9ea01a078b632185992a3a7ac448/package/ego-browser/scripts/real-browser-e2e/cases/index.mjs), [실행 명령](https://github.com/citrolabs/ego-lite/blob/aecc5831fc5a9ea01a078b632185992a3a7ac448/package/ego-browser/package.json), [CI](https://github.com/citrolabs/ego-lite/blob/aecc5831fc5a9ea01a078b632185992a3a7ac448/.github/workflows/ci.yml).

### 고정 조작 시간: 5개 시나리오 × 경로별 3회

공개 비교 실험은 The Internet 테스트 사이트에서 다음 작업을 실행한다. 각 동작의 전송 여부가 아니라 마지막 페이지 상태로 성공을 판정한다.

| 시나리오 | 성공 조건 | ego(lite) 중앙값 | 비교 제어 경로 중앙값 |
| --- | --- | ---: | ---: |
| 로그인 | secure URL과 성공 문구 | 1.076초 | 9.685초 |
| 비동기 컨트롤 | checkbox 제거, 입력 활성화·값 확인 | 7.431초 | 13.012초 |
| 요소 추가·삭제 | 3개 생성 후 2개 제거, 1개 남음 | 1.806초 | 15.346초 |
| 표 추출 | 최대 금액 행의 사람·이메일·금액 일치 | 9ms | 284ms |
| 로그인 세션 새로고침 | 새로고침 뒤 인증 상태 유지 | 450ms | 2.358초 |

**위 수치는 공급자가 공개한 측정값이며 이번 조사에서 재현하지 않았다.** 비교 제어 경로는 macOS 접근성 트리·스크린샷으로 native Chrome을 조작하는 Computer Use이다. 동일 브라우저에 다른 API만 붙인 실험은 아니다.

타이머는 대상 페이지 로드 뒤 시작하며 관찰·조작·대기·최종 확인을 포함한다. 최초 탐색과 모델 추론은 제외한다. 양쪽 모두 15/15회 성공했고, 원시 시간 30개와 제외한 파일럿 3건을 공개한다. cold start·캐시·프로세스 초기화가 완전히 일치했다는 근거는 없다. 3회 표본으로 p95나 일반 웹 신뢰성을 주장할 수 없으며, 토큰·비용도 측정하지 않았다. 근거: [실험 방법](https://lite.ego.app/article/codex-computer-use), [원시 데이터](https://lite.ego.app/article/codex-computer-use/benchmark-data.json).

### 실제 업무 평가: 같은 모델로 31개 과제 수행

현재 공개 README는 같은 31개 실사이트 과제를 `pi`, `gpt-5.6-sol`, reasoning effort `max`로 실행하고, 동일 judge·과제별 rubric·중단 조건을 적용했다고 설명한다. 브라우저 도구와 도구별 호출 스킬이 달라지는 비교다. 모든 요구사항을 만족해야 완전 성공으로 센다.

| 지표 | ego-browser | playwright-cli |
| --- | ---: | ---: |
| 평균 turns | 26.5 | 44.0 |
| rubric 평균 | 98.8% | 84.7% |
| 완전 성공률 | 93.5% | 71.0% |
| 평균 소요 시간 | 398초 | 648초 |
| 평균 비용 | $1.64 | $3.42 |

표는 공개 이미지의 `All rounds pooled` 값을 옮겼다. ego-browser와 chrome-devtools-cli는 1라운드, 나머지 3개 도구는 2라운드다. ego-browser 표본은 2026-08-25의 `be48d11` 빌드이며, 이번에 읽은 최신 SDK와 다르다. 반복 횟수 차이 때문에 변동성을 같은 정밀도로 비교할 수 없다. 확인한 공개 트리·README에서는 이 31개 과제의 실행기와 과제별 원시 결과를 찾지 못했다. 근거: [README](https://github.com/citrolabs/ego-lite/blob/aecc5831fc5a9ea01a078b632185992a3a7ac448/README.md), [원본 비교표](https://github.com/citrolabs/ego-lite/blob/aecc5831fc5a9ea01a078b632185992a3a7ac448/docs/assets/real-world-bench.jpg).

수치 해석도 구분해야 한다. 648초에서 398초는 **시간 38.6% 감소**이고, 같은 작업량 기준 속도비는 **약 1.63배**다. 제품 페이지의 “63% faster”를 “시간 63% 단축”으로 옮기면 부정확하다. 또한 위 비용은 해당 모델·실행 조건의 공개 결과이며 브라우저 자체의 가격이나 일반적인 절감률이 아니다. 근거: [제품 설명](https://www.egolite.app/solutions/browser-testing), 위 비교표에서 직접 계산.

## 3. 외부 에이전트 브라우저 수준의 평가 방식

### 공개 과제를 실행하고 작업 증거를 채점

| 평가 묶음 | 구성 | 채점 방식 | 주로 확인하는 능력 |
| --- | --- | --- | --- |
| [Online-Mind2Web](https://github.com/OSU-NLP-Group/Online-Mind2Web) | 136개 사이트, 300개 과제 | 작업 결과의 성공/실패. 원 평가기는 핵심 요구·행동 기록·주요 스크린샷을 조합 | 실제 사이트의 탐색·검색·폼·상태 변경 |
| [Odysseys](https://github.com/ljang0/Odysseys) | 200개 장기 과제 | 요구사항별 0/1 점수, 과제 평균, 모든 요구를 충족한 비율, 단계 대비 점수 | 여러 사이트를 오가는 장기 작업과 부분 진척 |
| [BU Bench V1](https://github.com/browser-use/benchmark#bu-bench-v1) | 5개 분야 각 20개, 총 100개 과제 | 정답·요구사항·실행 기록을 이용한 판정 | 웹 읽기, 복합 업무, 상호작용, 조사·추론 |

BU Bench V1의 분야는 WebBenchREAD, Online-Mind2Web 2, InteractionTests, GAIA, BrowseComp다. 현재 원 저장소의 기본 실행은 200개 과제의 V2.1이므로 V1 결과와 섞으면 안 된다. Online-Mind2Web도 과제 수정 이력을 제공한다. 이름이 같아도 데이터 revision·과제 ID 목록·실행 날짜를 고정해야 비교할 수 있다.

외부 공개 CLI runner에서 확인한 절차는 다음과 같다.

1. 과제·분야·난이도·모델·thinking 설정을 읽고 과제별 출력 디렉터리를 만든다.
2. 과제 지시를 CLI에 전달한다. 조사한 BU/Odysseys runner의 기본 동시 실행 수는 6, 과제 timeout은 30분이다.
3. stdout·stderr·구조화 이벤트를 보존하고 trajectory를 만든다. Odysseys 경로는 이벤트에서 스크린샷도 추출한다.
4. 실행 종료 후 별도 LLM judge가 채점한다. BU 경로는 정답이 있으면 우선 적용하고, Odysseys는 요구사항마다 판정한다.
5. 과제 결과 JSON과 전체 요약을 저장한다. 성공·실패·실행/채점 오류를 나누며, BU 경로는 수행 불가능 판정도 별도로 집계한다.

이 방식은 클릭 응답 속도를 직접 측정하는 것이 아니다. 모델이 어디를 보고 무엇을 선택하며 실패에서 어떻게 복구하는지까지 포함한 업무 평가다. 수행 불가능 과제를 제외한 성공률은 전체 과제 기준 성공률과 함께 표시해야 한다.

### 공개 실행 코드를 읽어야 드러나는 비교 조건

아래는 익명화한 외부 runner의 `run.ts`, `trajectory.ts`, `grader.ts` 및 공개 결과 요약을 정적으로 대조한 내용이다. 과거 발표 결과가 틀렸다는 판정이 아니라 재현 시 확인할 조건이다.

- **200 steps의 의미:** 조사한 Odysseys runner의 `--max-steps`는 실행 후 채점용 trajectory를 만들 때 적용한다. CLI 실행 인자에는 전달하지 않는다. 이 값만으로 에이전트 실행 자체가 200단계에서 중단됐다고 볼 수 없다.
- **발표 설정과 현재 runner의 차이:** 보관된 결과는 fast mode를 사용했다고 기록하지만, 현재 runner는 요약에 `fastMode: false` 또는 `fast_mode: false`를 기록한다. 현재 소스 실행만으로 과거 조건이 재현된다고 가정하면 안 된다.
- **시간의 경계:** 과제 `duration`은 CLI 실행과 결과 파일·trajectory 준비를 포함하고 judge 호출 전에 확정한다. 전체 실행 시간은 judge 대기까지 포함할 수 있다. 병렬 실행에서는 개별 과제 시간의 합과 전체 경과 시간도 다르다.
- **judge가 보는 증거:** 조사한 BU 경로는 stdout·이벤트 요약으로 채점하고 스크린샷 부재 자체를 실패로 보지 않는다. Odysseys 경로는 스크린샷을 전달한다. 같은 “LLM 채점”이어도 증거가 같지 않다.
- **부분 점수의 분모:** 전체 rubric 항목의 통과율과 과제별 rubric 평균의 평균은 다르다. 해당 runner의 집계 `average_rubric_score`는 전체 항목 기준이다. 원 Odysseys의 과제 평균 지표와 비교할 때 식을 맞춰야 한다.

예를 들어 1개 요구를 모두 만족한 과제와 9개 요구 중 1개만 만족한 과제가 있다면, 전체 항목 통과율은 2/10 = 20%지만 과제별 평균의 평균은 약 55.6%다. 둘 다 유효한 지표이나 같은 이름으로 보고하면 안 된다.

## 4. Flowmux가 이미 갖춘 검증과 부족한 계측

| 현재 근거 | 이미 확인하는 내용 | 성능 비교에 더 필요한 내용 |
| --- | --- | --- |
| [`test-browser-control.py`](../scripts/test-browser-control.py), `main` | 별도 GUI·로컬 fixture·독립 runtime/config/data/state/cache에서 실제 CLI 검사 | 고정된 빌드·환경의 반복 측정과 원시 결과 저장 |
| 같은 파일의 `exercise`, `exercise_regressions` | native 입력, 팝업·파일·미디어, frame/shadow, 잘못된 대상 거절, 최종 상태 | 명령 응답과 결과 확인 시간 분리, 실패율·중복 부작용 집계 |
| `exercise_compact_snapshot` | compact에서 정보·조작 의미 보존, DOM 무변경, stale ref 거절 | full/compact/find의 시간·출력 토큰·재탐색 횟수 |
| `BROWSER_SNAPSHOT_BUDGET` 출력 | full/부분 snapshot의 UTF-8 byte 수 | 페이지 규모별 분포와 목표 노드 발견율 |
| [`test-browser-wayland.py`](../scripts/test-browser-wayland.py) | 별도 데스크톱의 portal·native 입력·권한·파일 선택 경로 | 권한 대기와 입력 지연 분리, 플랫폼별 결과 |
| [`test-ci.sh`](../scripts/test-ci.sh) | 제한 시간 안의 회귀 검사 완료 | 성능 baseline·표본 수·p50/p95·회귀 판단 |

**Flowmux에는 기능 E2E 기반과 일부 출력 크기 계측이 있다. 조사한 브라우저 검사에는 반복 지연 분포나 모델 비용을 비교하는 완성된 성능 runner가 없다.** 기존 테스트 전체의 실행 시간은 녹화 길이, 의도한 timeout, fixture 대기를 포함하므로 클릭 성능 지표로 쓰기 어렵다.

테스트 파일을 읽었다는 사실과 이번에 테스트를 실행했다는 사실도 구분한다. 이 조사에서는 기존 검사들을 다시 실행하지 않았다.

## 5. Flowmux에 적용할 최소 측정안

다음은 확인된 구현 목록이 아니라 **후속 실측을 위한 제안**이다. 기존 fixture·CLI·격리 실행 구조를 재사용하고 새로운 SDK나 브라우저 엔진을 먼저 만들 필요는 없다.

### 고정 시나리오: 조작 기능과 지연

| 묶음 | 시나리오 | 성공 증거와 함께 기록할 값 |
| --- | --- | --- |
| 관찰 | 작은 문서·큰 표·많은 컨트롤에서 full/compact/find | 목표 발견율, truncated, 출력 bytes/모델 토큰, 시간 |
| 입력 | click/fill/type/press, 한글·contenteditable | 실제 값·이벤트·선택 위치, 명령 응답/상태 확인 시간 |
| 대기 | 지연 활성화·overlay·SPA 갱신 | 목표 상태 도달, 불필요한 재호출 수, timeout 비율 |
| 폼 | 여러 필드 개별 입력과 `form` | 모든 값·validation 결과, 호출 수, 총 시간 |
| 참조 | DOM 교체·부분 snapshot·탭 전환 | 오래된 ref의 잘못된 조작 0회, 새 관찰·복구 시간 |
| 구조 | same-origin iframe·open shadow | 정확한 노드 조작. cross-origin 미지원은 별도 기록 |
| 파일·탐색 | 팝업·업로드·다운로드·reload | 도착 URL, 서버 수신/파일 내용·해시, 세션 유지 |
| 제어·동시성 | 작업 중단·사용자 인계, 독립 1/2/4개 작업 | 중복 실행·다른 탭 오조작, 작업별 지연, 처리량 |

`input_delivered`를 업무 성공으로 세지 않는다. receipt의 `outcome_confirmed`도 지정한 조건을 관찰했다는 의미이므로, 저장·업로드 작업은 fixture 서버 상태나 실제 파일 내용으로 별도 판정한다. `ready-state=complete` 역시 SPA 작업 완료를 보장하지 않는다. 근거: [Flowmux 브라우저 계약](browser-workflow.md), [기존 검증 시나리오](browser-workflow-validation.ko.md).

초기 표본 수는 빠른 고정 조작마다 준비 실행 5회 뒤 본 측정 100회를 제안한다. 준비 실행도 기록하되 집계에서 구분하고, 매회 fixture 상태를 복구한다. 느린 파일·전체 workflow는 별도 표본 계획으로 운영한다. 서로 다른 작업의 시간을 한 분포에 섞지 않는다. 작은 파일럿 표본은 중앙값과 원시 값만 보고하고, p95를 안정된 수치로 해석하지 않는다.

### 실제 업무: 동일 모델의 완전 성공률·시간·비용

초기에는 공개 과제에서 범주를 나눠 고른 30개를 도구별 3회씩 실행하는 정도가 적절하다. 이는 비용과 채점 오류를 확인하는 파일럿 제안이며, 전체 벤치마크 점수로 발표하지 않는다. 본 비교는 동일한 전체 과제 집합과 동일한 반복 수로 수행한다.

모델·reasoning·프롬프트·스킬 버전·컨텍스트·권한 모드·로그인 상태·timeout·재시도 예산·동시 실행 수를 고정한다. 실행 순서를 교차하거나 무작위화해 시간대와 사이트 변화 영향을 줄인다. 첫 시도 결과와 재시도 결과를 모두 보존하며 가장 잘 나온 실행만 고르지 않는다.

페이지 UI 조작 트랙과 직접 HTTP/API·임의 JS 추출을 허용하는 트랙은 구분한다. 도구 하나의 배치 호출에 내부 조작 여러 개가 들어갈 수 있으므로 **LLM 호출 수, 도구 호출 수, 실제 브라우저 조작 수**를 따로 센다. 모델 round-trip 감소와 개별 클릭 개선을 구별하기 위해서다.

### 기록할 지표와 비교 규칙

| 항목 | 권장 기록 |
| --- | --- |
| 정확성 | 전체 과제 기준 완전 성공률, 과제 평균 rubric, 전체 항목 통과율, 실패·timeout·불가능·지원 불가·채점 오류 수 |
| 시간 | 초기 실행 준비, 각 명령 응답, 목표 상태 확인, 사용자 요청부터 완료까지의 전체 시간, judge 시간 |
| 비용 | input/output/cache/reasoning 사용량의 제공되는 구분, 단가 적용일, 실행·judge 비용, 실패를 포함한 총비용/성공 과제 수 |
| 관찰 비용 | 필터 적용 전 응답 bytes, 실제 tokenizer 기준 토큰, snapshot/find 횟수, 재탐색·스크린샷 수 |
| 환경 | OS·엔진·앱·SDK/CLI commit, CPU/RAM, 전원 모드, viewport·배율, 프로필·캐시 조건, 네트워크, 과제 revision |
| 근거 | task/run ID, 원시 시간, 행동·결과 이벤트, 최종 상태, 필요한 스크린샷·파일 검증값, judge 이유 |

실행 환경은 release 등 동일한 빌드 방식으로 맞춘다. coverage/debug 계측 결과와 일반 빌드를 섞지 않는다. 플랫폼 간 비교는 OS·엔진 차이를 명시하고, cold/warm 실행과 사람의 승인 대기는 분리한다. Linux X11·Wayland·macOS 결과도 따로 표시한다. Wayland 전경 native 입력은 동시 포커스 조작과 충돌할 수 있으므로, 독립 창의 동시 UI 입력을 무조건 지원한다고 가정하지 않는다.

시간은 monotonic clock으로 측정한다. 로컬 명령 p50/p95와 실제 업무 완료 시간을 각각 보고하고 실패·timeout을 누락해 빠르게 보이게 만들지 않는다. 성공 실행의 지연을 별도로 보여줄 경우 그 표본 수와 전체 성공률을 같이 표시한다. 토큰 비교는 RTK 등 출력 필터 적용 전의 도구 응답과 실제 모델 usage를 구분한다.

업무 성공률에는 신뢰구간을 붙이고, 동일 과제의 반복 실행은 독립 과제처럼 표본 수를 부풀리지 않는다. 반복 수가 충분하면 과제 단위 paired 분석이나 bootstrap으로 차이의 불확실성을 확인한다. 속도 회귀 임계값은 실제 baseline 변동을 본 뒤 정한다. 이번 조사에서 임의의 ms 목표나 경쟁 제품 대비 우위를 확정하지 않는다.

## 6. 먼저 할 일과 분석의 한계

우선순위는 **기존 로컬 fixture에서 관찰→조작→결과 확인의 시간·출력 크기를 기록하고, 같은 시나리오를 반복 실행하는 것**이다. 그다음 `compact/find`, `form`, typed wait/receipt가 호출 수와 전체 작업 시간을 얼마나 줄이는지 비교한다. 이 단계가 안정되면 동일 모델의 공개 업무 과제로 확대한다.

새 실행기를 크게 만들기보다 `test-browser-control.py`의 fixture와 독립 GUI 설정을 재사용하고, 필요한 시나리오의 측정·JSONL 기록·요약만 추가하는 접근이 적절하다. 기능 회귀 검사는 그대로 유지하고, 성능 결과에는 실패 실행도 남긴다. 이번 산출물은 분석 문서이며 해당 구현을 추가하지 않았다.

실측·제품 설치·모델 호출·공개 과제 실행은 하지 않았다. 현재 세션의 Flowmux 연결은 지정된 소켓 파일이 없어 `ping`에 실패했으며, 사용자 앱을 재시작하거나 다른 창으로 연결하지 않았다. 공개 문서·코드·비교표는 검색 도구와 GitHub 연결로 확인했다. 공급자 발표 수치와 정적 코드 분석만으로 현재 Flowmux의 상대 성능을 판단할 수 없다.
